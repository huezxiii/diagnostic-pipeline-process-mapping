How the numbers were made

A seeded Python generator writes an LIS-style event log. A pandas script mines it, a PostgreSQL query suite re-derives the same figures, and the dashboard, case study and deck all read the result.

01 · Synthetic event log

20,000 orders, eight timestamps each

Each row is one lab order in one scenario. Stage durations are never stored; they are mined from the timestamps, the same way a real LIS export would be analysed.

Generation

  • Seed 42, 10,000 orders per scenario over a 12-week window. The same order population (source, facility, true STAT, critical flag) runs through both scenarios, so comparisons are like-for-like.
  • Dock arrival is sampled first: in the As-Is scenario exactly 60% of clinic specimens arrive between 16:00 and 17:59. Earlier timestamps are subtracted from it and later ones added.
  • Stage times are gamma-distributed with multipliers for source, priority and arrival hour, then rescaled to the plan's baseline means. Rates (STAT, re-key, rejection, exceptions) are assigned by exact counts.

Timestamps per order

  1. ts_ordered → ts_drawn: order to draw
  2. ts_drawn → ts_dispatched: clinic holding bin
  3. ts_dispatched → ts_received: courier transport
  4. ts_received → ts_exception_cleared: exception hold
  5. ts_exception_cleared → ts_accessioned: accessioning
  6. ts_accessioned → ts_resulted: sort and testing
  7. ts_resulted → ts_verified: verification and EHR sync

Assumption. The project plan reports totals only, so the 1,116-minute As-Is cycle was allocated across stages: order to draw 95, clinic hold 168, transport 110, exception hold 153, accessioning 270, testing 162 (42 value-added), verification and sync 158. The To-Be cycle (276 minutes) is allocated the same way.

02 · Process mining

Stage latency mined from timestamps

analysis/process_mining_analysis.py derives every stage duration from consecutive events, ranks stages by non-value-added minutes and classifies path variants. Its output, metrics.json, feeds the case study and the deck.

def stage_durations(df: pd.DataFrame) -> pd.DataFrame:
    """Mine per-stage durations (minutes) from event timestamps."""
    def mins(a, b):
        return (df[b] - df[a]).dt.total_seconds() / 60.0

    return pd.DataFrame({
        "scenario": df["scenario"],
        "order_to_draw": mins("ts_ordered", "ts_drawn"),
        "clinic_hold": mins("ts_drawn", "ts_dispatched"),
        "transport": mins("ts_dispatched", "ts_received"),
        "exception_hold": mins("ts_received", "ts_exception_cleared"),
        "accessioning": mins("ts_exception_cleared", "ts_accessioned"),
        "testing": mins("ts_accessioned", "ts_resulted"),
        "verify_sync": mins("ts_resulted", "ts_verified"),
        "tat": mins("ts_ordered", "ts_verified"),
    }, index=df.index)

03 · SQL suite

The same answers, in PostgreSQL

sql/diagnostic_pipeline_analytics.sql re-derives the metrics with CTEs, EXTRACT(EPOCH …) interval math, PERCENTILE_CONT, RANK() OVER and a rolling AVG() OVER. Results below were captured by running the file; tests/test_sql.py checks they match the Python output.
